## 1. Цель: что значит «готово»

Пайплайн `load → preprocess → features → analyze → plot` проходит в Docker на всех данных
и даёт таблицы и графики для презентации. Требования курса:

| Требование | Где закрывается | Задачи |
|---|---|---|
| Реальный датасет, категориальные и числовые признаки | человеческий код (webdproc, PROGpedia, CodeNet) + ИИ-код | A1, A2, A3, A4 |
| Загрузка, пропуски, дубликаты, типы (NumPy, Pandas) | `DatasetLoader`, `CodePreprocessor` | A2, A5 |
| ООП: ≥2 класса, модули | все классы в `src/ai_code_detector/` | каждый в своих задачах |
| ≥3 техники анализа | `CodeAnalyzer`: статистика, группировка, корреляция, PCA | B2 |
| ≥3 типа графиков (Matplotlib) | `Visualizer`: распределения, категориальные, связи | B3 |
| PEP8, docstrings | `ruff check .` | каждый в своих задачах |
| Презентация 15 минут | слайды | A7, B4, B5 |

## 2. Кто за что отвечает

Каждый файл имеет одного владельца. Чужой файл меняем только через договорённость.

| Владелец | Файлы |
|---|---|
| **Nelson** | `data/*` (схема, источники, загрузка, предобработка), `generation/*`, `pipeline/data.py`, `cli.py`, `config.py`, `scripts/*`, `pyproject.toml`, `Dockerfile`, `docker-compose.yml`, `.github/*`, `README.md`, секции `sources` и `preprocessing` в `configs/default.yaml` |
| **Arpi** | `features/*`, `analysis/*`, `visualization/*`, `pipeline/analysis.py`, секция `features` в `configs/default.yaml` |
| **Тесты** | каждый пишет тесты к своим модулям в своих файлах: `tests/test_<модуль>.py` |

Общих файлов, которые правят оба, нет. Единственное исключение — `configs/default.yaml`:
каждый меняет только свою секцию, git сливает такие правки без конфликтов.
Если Arpi нужна новая библиотека, она пишет Nelson, и он добавляет её в `pyproject.toml`.

## 3. Контракты между частями

Части стыкуются только через эти таблицы. Пока контракт не меняется, Nelson и Arpi не мешают друг другу.
Изменение контракта обсуждаем вдвоём заранее.

| Таблица | Кто создаёт | Кто читает | Колонки |
|---|---|---|---|
| `data/interim/records.parquet` | Nelson (`load`) | Nelson | колонки `CodeRecord`: `record_id, code, language, label, label_status, source, task_id, dataset, author_id, created_at, generator, prompt_style, extra` |
| `data/interim/tasks.parquet` | Nelson (`load`) | Nelson (генерация) | `task_id, dataset, language, title, statement, statement_format` |
| `data/processed/clean.parquet` | Nelson (`preprocess`) | Arpi | те же колонки, что в `records.parquet`, после очистки |
| `data/processed/features.parquet` | Arpi (`features`) | Arpi | колонки `clean.parquet` + числовые признаки |

`label` — только `human` или `ai`. Признаками считаются все колонки, которых нет в `CodeRecord`,
поэтому имена признаков не должны совпадать с колонками `CodeRecord`.

**Когда таблицы появляются у Arpi:**

| Дата | Что есть в `clean.parquet` |
|---|---|
| 5 окт (после A2) | весь человеческий код, базовая очистка |
| 6 окт (после A3) | + первые ИИ-решения: 10 задач × 3 модели. Можно проверять сравнение `human` vs `ai` |
| 7 окт (после A4, A5) | полный датасет, финальная очистка |

Колонки таблицы не меняются, меняется только количество строк.
Выгрузку webdproc Nelson передаёт Arpi закрытым каналом (не через git). Без неё `load` работает
на PROGpedia и CodeNet.

## 5. Правила работы

1. **Ветка на задачу:** `feat/<id>-<кратко>`, например `feat/b1-features`. В `main` напрямую не пушим.
2. **Pull request на каждую задачу.** Ревью делает второй участник в течение суток; если ревью
   нет дольше суток, автор мержит сам, чтобы не блокировать работу. Мелкие PR лучше больших.
3. **Перед PR в Docker:** `docker compose run --rm app ruff check .` и `docker compose run --rm app pytest`.
4. **Данные и ключи не попадают в git.** Данные в `data/` (уже в `.gitignore`), API-ключи в `.env`.
5. **Синхронизация 15 минут в день:** что сделано, что дальше, где застрял.
6. **Задачи из таблицы выше заводим в GitHub Issues** с владельцем; PR ссылается на issue.
7. **Перед началом работы — `git pull` из `main`**, ветку держим короткой (1–2 дня), чтобы не
   расходиться с основной веткой.
